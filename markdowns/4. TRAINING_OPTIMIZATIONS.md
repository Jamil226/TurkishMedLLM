## 1. Memory Optimization Techniques

### 1.1 4-Bit Quantization (NF4)
**What:** BitsAndBytes 4-bit NF4 quantization of model weights  
**Impact:** Reduces model size from ~14GB (full precision) to ~8GB effective  
**Implementation:**
```python
BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_use_double_quant=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16
)
```
**Result:** ✅ Model loads successfully, no OOM during load phase

---

### 1.2 Gradient Checkpointing
**What:** Trade computation time for memory by recomputing activations during backward pass  
**Impact:** Saves ~30-40% GPU memory during training  
**Implementation:**
```python
self.model.gradient_checkpointing_enable()
```
**Applied in:** `load_model_and_tokenizer()` function  
**Result:** ✅ Enables smaller batch sizes without memory spikes

---

### 1.3 Batch Size Reduction
**Original Configuration:**
- Batch size: 8 per device
- Eval batch size: 8
- Result: ❌ CUDA OOM errors during forward pass

**Optimized Configuration:**
- Batch size: **2 per device** (reduced 4x)
- Eval batch size: **2 per device** (reduced 4x)
- Gradient accumulation: 4 steps (maintains effective batch size of 8)
- Result: ✅ Stable training at 31.8GB/32.7GB GPU utilization (97%)

**Trade-off:** More total steps (105,395 instead of ~26,345), but fit within memory

---

### 1.4 LoRA (Low-Rank Adaptation)
**What:** Fine-tune only adapter weights instead of full model  
**Configuration:**
- Rank (r): 16
- Alpha: 32
- Dropout: 0.05
- Target modules: q_proj, v_proj, k_proj, o_proj, gate_proj, up_proj, down_proj

**Impact:** Reduces trainable parameters from 7B to 40.37M (0.92% of total)  
**Result:** ✅ Dramatically reduces memory and compute requirements

---

### 1.5 Efficient Optimizer (PagedAdamW 32-bit)
**What:** Memory-efficient version of AdamW optimizer  
**Impact:** Optimizer states fit in VRAM instead of CPU RAM  
**Result:** ✅ Keeps entire training on GPU, no host memory overhead

---

### 1.6 Environment Variable Configuration
**What:** Enable PyTorch CUDA memory expansion  
**Implementation:**
```bash
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
```
**Impact:** Allows dynamic memory allocation without fragmentation  
**Result:** ✅ Prevents spurious OOM errors from memory fragmentation

## 7. Key Lessons Learned

1. **Quantization + LoRA is essential** for fine-tuning large models on limited VRAM
2. **Gradient checkpointing trades time for memory** - worth it when memory-bound
3. **Batch size reduction cascades** - small batch = many more steps, doubles training time
4. **GPU memory fragmentation is real** - `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` prevents spurious OOM
5. **Parameter names in HuggingFace evolve** - always validate against current library version
6. **Monitoring GPU memory is critical** - 97% utilization leaves no room for error

## 8. Future Optimization Opportunities

| Option | Trade-off | Feasibility |
|--------|-----------|-------------|
| Reduce sequence length to 1024 | May lose long-context info | ⚠️ Moderate |

| Use alternative quantization (int8) | Slightly less compression | ⚠️ May cause instability |
| Reduce LoRA rank to 8 | Fewer parameters to adapt | ⚠️ May reduce learning capacity |
| Distributed training across GPUs | Requires multi-GPU setup | ❌ Not available |

**Recommendation:** Current setup is optimized to the maximum for available hardware. Further optimization would require hardware upgrades or model size reduction.
